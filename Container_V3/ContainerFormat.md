# Container format V3

V3 — это исправленный V2. Формат намеренно совместим по идее, но заголовок расширен,
поэтому файл V2 читаться не будет (см. "Чем отличается от V2" ниже).

## Статус версий: 1 и 2 — итерации разработки, а не поддерживаемые форматы

Версии в этом проекте нужны как шаги развития, поэтому поддержка чтения старых файлов
**не предусмотрена**: никакой обратной совместимости по байтам, никаких адаптеров и
«режимов совместимости». `Magic` + `Version` существуют ровно для одного — чтобы чужой
или устаревший файл отклонялся явно, а не читался криво:

| Версия | Статус | Что делает V3 |
|--------|--------|---------------|
| 1 (`Container.cs`) | итерация, снята с поддержки | отклонён по magic/version |
| 2 (`ContainerV2.cs`) | итерация, снята с поддержки | отклонён по magic/version |
| 3 (`ZST3`) | текущая | пишется и читается |

Практическое следствие: старый контейнер не «открывается частично» — источник переупаковывается
текущей версией. Это сознательный отказ, а не недоделка; он снимает половину сложностей,
которые тащил бы за собой режим совместимости (разные длины bool, varint в путях, отсутствие
`ChunkSize` в заголовке).

Правило на будущее: если понадобится изменение layout, оно получает новую `Version`, и
прежняя версия перестаёт читаться. Совместимость внутри версии не гарантируется между версиями.

## Общий вид

```
[HEADER][CCHUNK_0][CCHUNK_1]...[CCHUNK_N-1][INDEX]
```

## HEADER — 36 байта, фиксированный размер

| Поле          | Тип        | Размер | Комментарий                                        |
|---------------|-----------|--------|----------------------------------------------------|
| Magic         | ASCII     | 4      | `"ZST3"`                                           |
| Version       | int32 LE  | 4      | `3`                                                |
| ChunkSize     | int32 LE  | 4      | размер чанка **до** сжатия. Носитель формата, а не настройка экземпляра |
| HashLength    | int32 LE  | 4      | длина хэша чанка в байтах (SHA-256 → 32)           |
| ZstdLevel     | int32 LE  | 4      | уровень сжатия, для диагностики/предупреждения     |
| OffsetToIndex | int64 LE  | 8      | абсолютное смещение блока INDEX в файле            |
| IndexCrc32    | uint32 LE | 4      | CRC32 **сжатого** блока индекса                    |
| HeaderCrc32   | uint32 LE | 4      | CRC32 первых 32 байт заголовка                     |

Зачем новые поля:

* `ChunkSize` — в V2 его не было, и распаковка брала размер чанка из текущего экземпляра
  (`maxDecompressedChunkSize = chunkSize`). Упаковал с 1 МБ, распаковал с 512 КБ → рассинхрон.
* `HashLength` — в V2 читался `_hasher.Length` от текущего экземпляра. Хэшер тоже должен быть
  свойством файла, а не объекта.
* `IndexCrc32` / `HeaderCrc32` — в V2 `TryValidateContainer` проверял ровно 4 байта magic.
  Теперь можно отличить «файл повреждён» от «это вообще не контейнер».

## CCHUNK — переменный размер

```
[CompressedData: (HashPosition - OffsetInContainer) байт][Hash: HashLength байт]
```

Хэш считается **по сжатым байтам** этого чанка, как в V2. Это даёт проверку целостности
на распаковке без знания исходных файлов.

Важно: длина распакованного чанка не равна `ChunkSize` для последнего чанка. Последний
чанк может быть заполнен частично (например 300 КБ из 1 МБ). Поэтому в индексе каждое
`CChInfo` хранит `UncompressedLength`.

## INDEX — сжатый Zstd блок, лежит в конце файла

Сначала два префикса в открытом виде:

```
[CompressedIndexLength: int64][UncompressedIndexLength: int64][CompressedIndexData]
```

После декомпрессии `UncompressedIndexLength` байт внутри всё так же, как в V2:

```
[OffsetTo_ChunksBlock: int64][OffsetTo_FilesBlock: int64]
  [ChunksCount: int32]
    [ChunkNumber: int32][OffsetInContainer: int64][HashPosition: int64][UncompressedLength: int32]   * ChunksCount
  [FilesCount: int32]
    [Path][Size: int64][IsEmptyFolder: bool(1 байт)][IsSplitted: bool(1 байт)][ChunkCount: int32]
      ([ChunkNumber: int32][OffsetInChunk: int32][BlockSize: int32]) * ChunkCount
```

Порядок внутри индекса фиксирован, и смещения блоков указывают **на своё поле счётчика**,
а не на первую запись: `OffsetTo_ChunksBlock` ведёт к `ChunksCount`, `OffsetTo_FilesBlock` —
к `FilesCount`. Читатель сам достаёт счётчик с этого места. В V2 эти смещения записывались
после счётчиков, и каждый читатель должен был помнить, на сколько байт сдвинуться, — именно
так появлялся «мусор» вместо первого пути.

Размер записи фрагмента — ровно 12 байт (`int32 + int32 + int32`). `OffsetInChunk` — int32,
а не int64: это смещение внутри одного чанка, а чанк по определению не больше `ChunkSize`,
который сам лежит в int32. В V2 это было поле long и тратило 8 байт на каждое описание
фрагмента.

Поля bool — ровно 1 байт. `BinaryWriter.Write(bool)` пишет 4 байта, и запись «bool» из одного
писателя читается другим как мусор; поэтому здесь всё пишется по явной схеме через BinaryPrimitives.

### Сериализация строк

V2 использовал `BinaryWriter.Write(string)`, то есть length-prefix в 7-bit varint и UTF-8.
V3 пишет путь явно: `[int32 длина в байтах][UTF-8 байты]`. Причина: varint кодирует длину
переменным числом байт, и любой парсер вне .NET обязан повторять именно это кодирование.
Фиксированный int32 проще и проверяемее.

Поле `IsDeleted` из V2 вырезано: нигде не записывалось со смыслом, везде `false`. Удаление новой
версии не потребовало: оно работает на уровне индекса, см. раздел «Изменение готового контейнера».

## Манифест (отличие от V2 по поведению)

V2 хранил только относительный путь и размер. Если файл изменился между сканированием и
чтением, `FillChunkWithDataSync` делал `if (read == 0) break;` и **молча оставлял нули** в
чанке: контейнер выглядел целым, хэш сходилась, распаковывался битый файл.

V3 перед упаковкой открывает файл и сверяет `Length` с тем, что дал сканер. Расхождение →
`ManifestMismatchException`, а не тихая дырка из нулей. Это отдельная ответственность:
`SourceManifest`, а не «где-то внутри упаковки».

## Изменение готового контейнера: дописывание, удаление, уплотнение

Формат при этом не меняется: версия остаётся 3, расположение блоков и записей индекса те же.
Меняется только то, как файл дозаписывается. Контейнер, собранный `pack` за один проход, и
контейнер, который пять раз дописывали и уплотняли, читателем не различаются.

### Дописывание

Добавление файлов не переупаковывает контейнер: иначе файл в несколько гигабайт пришлось бы
пересобирать целиком. Делается то же, что при упаковке с нуля, только окно сдвинуто:

1. Заголовок и индекс читаются, CRC и границы чанков проверяются до первой записи.
2. Новые данные дописываются после конца файла — **после старого индекса**, а не вместо него.
   Номера новых чанков продолжают старые: `первый новый номер = количество чанков в старом индексе`.
3. Новый индекс — старые записи плюс новые — сериализуется, сжимается и дописывается в конец.
4. `FlushToDisk()`, затем `PatchHeader`: 16 байт (`OffsetToIndex` и `IndexCrc32`) на смещении 20.

Точка коммита одна — именно эти 16 байт. До них файл по старому `OffsetToIndex` читается ровно
как раньше, после них — как новый. Запись оборвалась посередине: старое значение всё ещё указывает
на старый индекс, и тот цел. Оборванный новый индекс после коммита обнаруживается по несовпадению
`IndexCrc32`. Сам старый индекс после коммита становится мусором.

Файл с таким же именем внутри контейнера заменяется: старая запись уходит из индекса, её чанки
остаются в файле и становятся мёртвыми. Имя внутри контейнера задаёт вызывающий (список панели
или CLI), а не диск: так `add C:\tmp\отчет.txt` может лечь в контейнер как `годовой отчёт.txt`.

### Удаление

Удаление не трогает данные. Записи, чьё имя совпадает с запрошенным или лежит под ним, исчезают
из индекса (папка удаляется целиком, сравнение имён без учёта регистра), и в конец дописывается
**только новый индекс**. Список чанков сохраняется целиком: номер чанка обязан совпадать с его
позицией в списке — `RestorePlanner` выбирает чанк по номеру, и пропуск в списке означал бы
распаковку не теми байтами. Осиротевшие чанки не вычёркиваются из списка, они просто больше
никем не упоминаются: мёртвые.

Запрос на удаление при этом не обязательно имя. `RemovalPattern` разбирает строку из списка на
удаление — из панели Total Commander или из CLI — и задаёт одну из трёх областей действия:

- **Exact** — имя без `*` и `?`: запись с таким именем и всё, что под ней. Так работает Del по имени
  папки.
- **Folder** — форма `папка\*.*` или `папка\*`, то есть ровно то, что панель присылает на Del по
  папке: удаляются сама папка и всё её поддерево. Пустая `Folder` (строка `*.*` из корня панели)
  означает всё содержимое контейнера.
- **Mask** — остальные строки с `*` или `?`: сравнение по сегментам пути, где `*` не переходит через
  `\`, а `?` заменяет ровно один символ; регистр не учитывается, как в Windows.

Имя внутри контейнера не может содержать `*` и `?` — их отбраковывает проверка имени при упаковке, —
поэтому строка с ними в запросе на удаление однозначно является маской, а не именем. Сегмент `..` и
двоеточие (имя с диском) отвергаются: удаление не может выйти за пределы контейнера. Если под запрос
не попала ни одна запись, удаление отвечает `NothingToRemoveException`; плагин превращает это в
`E_NO_FILES` («нет файлов для удаления»), а не в отказ «плагин такого не умеет».

Поэтому после удаления файл не уменьшается — он обычно чуть вырастает, на размер нового индекса.

Отдельная тонкость — пустые папки. Отдельных записей о промежуточных папках индекс не хранит:
папка существует ровно пока под ней лежит хотя бы одна запись. Чтобы папка, из которой удалён
последний файл, не исчезла из списка (в отличие от обычной папки на диске), удаление дописывает
в новый индекс нулевую запись с `IsEmptyFolder = true` про самую глубокую освободившуюся папку;
через неё видны и все её родительские папки, а распаковщик создаёт их на диске пустыми. Для папки,
которую пользователь удалил по её собственному имени, и для папок внутри такой папки запись не
создаётся: иначе Del над папкой нельзя было бы повторить. Записи о пустых папках, оставленные
удалением, переживают уплотнение — плотная перенумерация чанков их не трогает.

### Уплотнение

Явная операция, отдельная от добавления и удаления: живые чанки переносятся **дословно** (без
пережатия и без потери хэшей), нумеруются плотно 0..N-1, ссылки фрагментов переставляются по
сопоставлению «старый номер → новый», новый индекс дописывается во временный файл, и тот заменяет
контейнер через `File.Replace`. Уплотнение, которому нечего уплотнять, файл не переписывает.

### Мусор и как его посчитать

| что появляется | откуда |
|---|---|
| мёртвые чанки | удалённые файлы; чанки файлов, заменённых по тому же имени |
| блоки вытеснённого индекса | каждая дозапись и каждое удаление оставляют старый индекс внутри области данных |

`ContainerHealth` считает это по файлу: область данных = `OffsetToIndex − 36`; каждый чанк
занимает `HashPosition − OffsetInContainer + HashLength`; `GarbageBytes` — то, что в области
данных не относится ни к живым, ни к мёртвым чанкам; `EstimatedSizeAfterCompact` = 36 + живые
чанки + нынешний индекс; `ReclaimableBytes` = размер файла − оценка. Команда `info` печатает
всё это, `NeedsCompact` — просто `ReclaimableBytes > 0`.

### Резервная копия перед изменением

Порог 100 МБ: контейнер не больше — перед изменением создаётся копия `<имя>.cc.bak`, поверх
прежней; больше — копии нет, изменение идёт на месте. Копия снимается **до** открытия файла на
запись, поэтому в ней ровно то, что было до изменения. Первое создание контейнера копии не делает.

## Чем отличается от V2 (кратко)

Только для истории — V2 не читается и переупаковывается.

|                  | V2                                   | V3                                        |
|------------------|--------------------------------------|-------------------------------------------|
| chunkSize        | только в экземпляре класса           | в заголовке файла                         |
| длина хэша       | из текущего `IHasher`                | в заголовке файла                         |
| последний чанк   | сжимался недозаполненным буфером     | явная длина, сжимается ровно данные       |
| проверка файла   | 4 байта magic                        | CRC32 заголовка + CRC32 индекса + хэш каждого чанка |
| битые исходники  | тихие нули в чанке                   | исключение на этапе упаковки               |
| дубли кода       | PackAllSF/MT, StoreNSFiles/P, ReassembleOneFile/P | по одной реализации, режим параллелизма — параметр |

## Что обязан сделать читатель

Читатель не доверяет ни одному полю индекса, пока не проверил CRC. Дополнительно проверяются
разумные границы: длина пути, длина индекса после распаковки, количество фрагментов относительно
оставшихся байтов, влезает ли фрагмент `[OffsetInChunk .. +BlockSize]` в фактическую длину
чанка и не выходит ли путь за пределы папки распаковки. Каждая из этих проверок — отдельное
исключение (`ContainerFormatException`, `ChunkIntegrityException`, `ReassemblyException`),
а не молчаливый выход из цикла.
